# Upgrade 26 — measured paused-field rendering cost

Release 0.28.0. Battle rules 17 and campaign envelope 21 remain unchanged.

## What changed

Paused battlefields previously built a full presentation snapshot and synchronized every formation on every rendered frame. This repeated formation poses, hit polygons, labels, flags, shadows and smoke even though field time was stopped.

A scene-local presentation cache now reuses that work while paused. Normal commands replace the cached snapshot. Advancing combat and outcome animations continue rebuilding it. Zoom, formation selection, hover, touch inspection and reduced-motion changes invalidate the sprite pass. Selection arcs, destination previews, group previews, map markers and tactical overlays still update independently. Resuming the battle runs the existing engine without a simulation shortcut.

An opt-in `?fieldProfile=1` overlay reports field-ready time, frame/update p95 and snapshot/formation-pass counts over 120 foreground frames. It is absent during normal play and sends no telemetry. Ready time starts at scene construction; it excludes initial application navigation and JavaScript download. Frame delta includes scheduling/rendering effects; update duration measures the scene's update method only. Neither metric measures total GPU work, battery use or memory.

## Local browser observations

Manassas, default Hold Henry Hill practice mission, desktop viewport, local production builds. Baseline is the previous renderer with identical diagnostic instrumentation. These are sampled windows on this Mac, not physical-phone or throttled-network benchmarks.

| Measure | Baseline | Updated |
|---|---:|---:|
| Paused update p95 | 1.20 ms | 0.10 ms |
| Paused frame p95 | 8.4 ms | 8.3 ms |
| Snapshot builds / 120 stable paused frames | 120 | 0 |
| Formation passes / 120 stable paused frames | 120 | 0 |
| Scene ready | 299 ms | 320 ms |
| Running update p95, sampled early battle | 1.90 ms | 1.80 ms |

The observed improvement is approximately **92% less paused update work**. Frame pacing was already near this display's refresh interval. The startup difference is small and does not establish a loading improvement. Running samples were taken at different early field times; they are sanity checks, not a controlled speedup claim.

Gettysburg at 390×844 recorded ready 304 ms, paused frame p95 8.4 ms, update p95 0.10 ms and zero snapshot/formation passes in a stable 120-frame window. This is viewport emulation on the same desktop hardware.

## Loading audit and next bottleneck

`scripts/audit-field-assets.mjs` invokes the production preload method with recording loaders for all 11 current-rule option-A boards. Unique on-disk preload bytes range from **37.76 MB at Shiloh to 47.77 MB at Cold Harbor**; Manassas loads 42.91 MB. These totals exclude initial app code and other campaign assets. They are neither network transfer measurements nor decoded-memory estimates. Shared image URLs are counted once per encounter.

This pass preserves all image files and preload behavior. The next high-value loading step is a reproducible asset-processing pipeline: reduce delivered image bytes and repeated startup compositing while preserving the original artwork, transparency and fallback behavior. Then measure cold/warm loading on constrained devices and networks. JavaScript chunk size, decoded memory, physical touch devices, and sustained active-combat performance remain open.
